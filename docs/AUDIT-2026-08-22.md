Technical audit and gap analysis of the NomadKids codebase against
`docs/reference/Project_Info.md` (the client's RFP).

The audit was requested as one of "an existing Next.js codebase" — checking
"PostgreSQL readiness" and finding the immediate priority "before moving to the
UI/UX design of the Teacher's Dashboard."

So the useful question is not "what do we build before the dashboard" but "what
is left, and what must land before more UI is built on top of it." That is what
this document answers.

## 4. Architecture review

### 4.1 Database

PostgreSQL 17 through Prisma 7 with `@prisma/adapter-pg`. Five reviewed
migrations. The RFP's "no SQLite in production" was never a risk here.

Three structural properties do the heavy lifting:

1. **`kindergartenId` on every tenant-scoped table**, even where a relation
   could reach it. Tenant isolation is one `WHERE` clause, not a three-join
   traversal somebody eventually forgets.
2. **Soft delete everywhere except `AuditLog`**, whose repository exposes only
   `append()`.
3. **`common/repository/tenant-scope.ts`** composes the base filter under `AND`,
   so a caller's condition cannot overwrite `deletedAt: null`. That detail is
   the difference between a helper and a guarantee.

Indexing is deliberate — composite indexes on `(kindergartenId, status)`,
`(childId, observedOn desc)`, `(childId, visibleToParents, observedOn desc)`,
and partial-unique constraints verified present after a restore.

**On scale, specifically.** What is verified is that the query _shapes_ are
bounded: every list except the media gallery (F2) goes through `toSkipTake`, and
`test/query-counts.test.ts` holds 8 N+1 guards — the group assessment grid
measures 2 queries for a group of 2 and 2 for a group of 20. What is **not**
verified is behaviour on a populated database. The largest dataset this codebase
has been exercised against is the test fixture; the backup drill in
`PHASE_1_ACCEPTANCE.md` reports `children=1`. See **F12**.

### 4.2 Authentication and authorization

The strongest part of the codebase, and built the right way round.

- The access token carries `userId` + `sessionId` **only**. Roles and
  kindergartens are re-read from `Membership` per request, so revoking a
  teacher takes effect immediately rather than at token expiry.
- Refresh tokens are an opaque rotating family; only the SHA-256 is stored;
  replaying a rotated token revokes the whole family.
- **All child-data authorization lives in `apps/api/src/authz/`** and resolves
  the kindergarten set from `Enrollment` history, never from
  `Child.kindergartenId`.
- **404, never 403** — 121 assertions across the integration suite.
- `test/authz-consistency.test.ts` holds the list query and the detail route to
  the same answer across 19 cases, so a child cannot appear in a list and 404 on
  their own page.
- The `PrismaClient` boundary is enforced by ESLint `no-restricted-imports` with
  a message citing CLAUDE.md §2.2, plus `test/prisma-boundary.test.ts`.

Media: `GET /media/:id` → authorization → 302 to a 5-minute presigned URL;
private bucket; `storageKey` a random UUID path. Uploads go through the API
(never a presigned PUT), are type-detected from magic bytes, re-encoded through
sharp (which is the EXIF strip), bounded to 2000px, and decompression-bomb
checked. A renamed executable is rejected — asserted, not assumed.

### 4.3 Next.js structure

One authenticated shell at `app/(app)/`, navigation derived from session roles.

**This deviates from CLAUDE.md §5, which mandates three shells — and the code is
right, the rule is wrong** (F9). The reasoning is written out at
`apps/web/app/(app)/layout.tsx:25`: Next resolves route groups into the same URL
space, so `(teacher)/children/[childId]` and `(parent)/children/[childId]` are a
build error, and prefixing the parent's routes would give one child two URLs and
break a link shared between a teacher and a parent. The client also has a
dual-role user (an admin who is also a parent).

The typed client in `lib/api/` sets `cache: "no-store"` by default
(`client.ts:106`), closing the per-URL-not-per-user caching trap. Media images
deliberately bypass `next/image`, because the optimiser would cache the object
behind a public `/_next/image` path — the exact rule the media design exists to
enforce.

### 4.4 Async work

BullMQ + Redis. PDF generation is enqueued **after** commit. The worker runs
in-process by default with `concurrency: 1` (one Chromium page measured at a
512 MB floor) and splits out via `REPORTS_WORKER_ENABLED=false` with no code
change. It refuses to boot if no Cyrillic font is installed — which catches the
`PDF_SPIKE.md` failure where Chromium renders _nothing_ and reports success.

### 4.5 Environments and double-submit (RFP §14, §17)

`NODE_ENV` is a validated enum with production-only invariants enforced at boot
in `config/env.ts:129`. Separation between dev / staging / production is by
environment variables and separate instances; `railway.json` defines a single
API service, so a staging deployment is a Railway environment rather than
anything in the repository.

Double-submit (§17) is handled on both sides but unevenly: the web app disables
controls on mutation-pending in 101 places, and the API is explicitly idempotent
for likes, read receipts and report jobs (BullMQ dedupes on `jobId`). There is
**no generic server-side idempotency key**, so a double-POSTed observation would
create two rows if the client guard were bypassed. Acceptable at this stage;
worth recording.

**Verdict on scalability.** The architecture is sound for the RFP's targets —
tenant isolation is structural, authorization is centralised, slow work is
queued, and the boundaries that matter are machine-enforced. The gap is
evidence, not design: it has not been run against data at §17 volume (F12).

**F1 · Assessment configuration has no write path.**
RFP §2.1 ("Хөгжлийн шалгуур, үнэлгээний мэдээллийг удирдах"), §5.2, §6.1 and
§6.2 all require domains, levels and observation types to be
administrator-editable. The tables exist and CLAUDE.md §2.3 is satisfied — but
there is **no create or update endpoint**. `GET
/kindergartens/:id/assessment-config` is read-only, and every repository touch
of `developmentDomain`, `assessmentLevel` and `observationType` is a
`findMany` / `findFirst` / `count`. The values are reachable only through
`prisma/seed.ts`. SECURITY.md §6.2 also lists
`test_a_director_cannot_open_a_system_domains_edit_form` as an acceptance case;
it cannot be reproduced, because the form does not exist.

**F2 · The child photo gallery is unbounded.**
`GET /children/:id/media` accepts only `purpose` — no page parameters
(`media.controller.ts:46`). `media.repository.ts:33` (`listForChild`) and `:65`
(`listVisibleForGuardian`) call `findMany` with no `take`. The web side matches:
`child-gallery.tsx:53` parses the response as `z.array(mediaSchema)` with no
page state, and every item renders a `MediaThumb` issuing its own
`GET /media/:id`. A child with 600 photos returns 600 rows and 600 signed-URL
redirects on one screen. This violates **CLAUDE.md §3.4** ("Every list is
paginated. No endpoint returns an unbounded set") and RFP §17. Every other list
— children, groups, users, observations, notifications, audit, reports — goes
through `toSkipTake`, which is what makes this an oversight rather than a policy.

**F3 · No kindergarten logo, on the record or in the PDF.**
RFP §3.2 requires лого and цэцэрлэгийн зураг on the kindergarten record;
`Kindergarten` (`schema.prisma:322`) has `name`, `address`, `phone`, `email`,
`description` and nothing else. RFP §10.3 makes the logo a PDF requirement
("Цэцэрлэгийн лого, нэртэй"); `portfolio-template.ts:179` renders the name only.
Schema change plus template change — cheaper now than after more report work.

**F4 · Missing profile and group fields.**
`User` has no profile photo (§3.3). `Group` has no class photo, schedule
(хичээлийн хуваарь) or group rules (бүлгийн дүрэм) (§3.2).

**F5 · Portfolio metadata gaps.**
No zodiac sign or Mongolian year-animal (§4.2) — pure functions over
`dateOfBirth`, no schema change, currently absent entirely. `MediaFile` has
`caption` and `order` but no `takenAt`, no age/category, and no uploader
attribution (§4.4); attribution is only inferable from `AuditLog`.

**F6 · No audit-log browser UI.**
`GET /audit` exists and is paginated; the web app consumes only the last few
entries on the admin dashboard. RFP §2.1 requires that an administrator can view
the audit log.

**F7 · The 108 acceptance cases have no traceability.**
SECURITY.md §6 names 108 cases as "the integration suite's specification," and
§15's first pre-launch box — "All 108 acceptance cases in §6 have an HTTP-level
test, and they pass" — is **unchecked**. The suite has ~592 integration tests
and 121 `toBe(404)` assertions, which is almost certainly enough coverage, but
nothing maps case → test. Today nobody can honestly tick that box, and nobody
can say which of the 108 is the missing one. A mapping table is a few hours and
it is the difference between "we think it's covered" and sign-off.

**F8 · Status documents are stale at the top.**
`IMPLEMENTATION_STATUS.md`'s summary table marks phases 11, 12 and 13 as ⬜
pending and states "**Git:** no commits." There are 56 commits, and the
document's own body has ✅ sections for all three phases — only the header is
wrong, but the header is what a reader trusts first. `PHASE_1_ACCEPTANCE.md`
item 5 is stale in the same direction: it records admin CRUD screens as
"deliberately not built," and they have since been built (`65845d3`, `733c941`,
`05e9dd9`). Item 15's "18 routes" is now 27.

**F9 · CLAUDE.md §5 contradicts the shipped shell architecture.**
§4.3 above. CLAUDE.md declares itself mandatory ("Code that violates a rule does
not get written"), so leaving this stands a real chance of a future session
"fixing" a correct implementation into a build error. Amend the rule to describe
one shell with role-derived navigation.

**F10 · HEIC is rejected where the RFP lists it as supported.**
RFP §4.4 names HEIC among required formats; `upload-validation.ts:102` detects
the HEIF family specifically in order to refuse it with a helpful Mongolian
message. The reasoning is sound and documented — sharp's prebuilt binary has no
HEVC decoder, and iOS converts to JPEG on `<input type="file">` anyway. This is
a **conformance gap with a defensible rationale**, not a defect; it needs to be
put to the client rather than quietly carried.

**F11 · No separate thumbnails.**
RFP §17 asks for thumbnails generated separately. Stored images are bounded to
2000px on the longest edge and `MediaThumb` serves those full-size. Acceptable
at current volume; it becomes a mobile-data problem on an album screen with
dozens of photos, and it compounds F2.

**F12 · Scale is designed for but not measured.**
§4.1. The §17 targets are 10 kindergartens, 100 groups, 300 teachers, 3,000
children, 6,000 guardians and thousands of photos. Nothing here has been run
against that. The missing evidence is small and specific: scale `pnpm seed:demo`
to §17 volume, then time and `EXPLAIN` three endpoints — the children list, a
child's observation list, and the group assessment grid.

## 7. Next steps

The dashboard already exists, so the honest priority is not "design the
dashboard." It is: **anything that changes the data model lands before more UI
is built on top of it.** Retrofitting a schema under finished screens is the
expensive path.

### Priority 1 — schema-level, first

1. **F3** — add a logo (and photo) to `Kindergarten`; render the logo in both
   PDF templates. RFP §3.2 + §10.3.
2. **F4** — `User` profile photo; `Group` class photo, schedule, rules.
3. **F1** — CRUD for `DevelopmentDomain`, `AssessmentLevel`, `ObservationType`,
   including the system-row-vs-override rule already modelled by the nullable
   `kindergartenId`. Carries the three mandatory authorization tests
   (CLAUDE.md §4.1) plus the system-row case from SECURITY.md §6.2.
4. **F2** — paginate the media list; the gallery component changes with it.
5. **F5** — `MediaFile.takenAt` / category / attribution now, while the album is
   still small. Zodiac and year-animal need no migration and can follow.
6. Decide **milestones (§4.5)** and **growth history (§7)** with the client
   _now_ — both are new tables, and both are far cheaper before the portfolio
   screens are finished than after.

### Priority 2 — sign-off blockers that are not features

7. **F7** — write the 108-case → test mapping. Then SECURITY.md §15 can be
   worked through and ticked with evidence.
8. **F12** — the seed-and-measure run above. It is the only outstanding answer
   to "will this hold at the contracted volume."
9. **F8, F9** — correct the stale documents. Ten minutes, and it stops the next
   session acting on wrong information.
10. **F10** — put HEIC to the client as an explicit decision.
11. `FINAL_DEVICE_QA.md` — needs a person with a phone. Blocks sign-off, not
    deployment.

### Priority 3 — then UI

12. The §12.1 teacher-dashboard tiles (birthdays today, term progress, domain
    averages) and the §12.2 admin tiles.
13. The audit-log browser (F6).
14. §11 filters and sorting.
15. Thumbnails (F11).

Only after 1–6 have landed does further dashboard and portfolio UI work sit on a
model that will not move underneath it.
