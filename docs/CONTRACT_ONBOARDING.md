## 1. Хамгийн эхэнд — энэ нь **нээлттэй маягт**, тэр нь эрсдэл

★★★ Алхам 2 бол системийн **анхны нэвтрэлтгүй бичих цэг**. Өнөөдөр
`@Public()` тэмдэгтэй зүйл гурав л байна: нэвтрэх/нууц үг сэргээх, `/health`,
QPay-ийн callback. Эхний хоёр нь юу ч үүсгэдэггүй, гурав дахь нь QPay-ийн
гарын үсгээр баталгаажна.

Шинэ маягт нь **хэн ч, хэдэн ч удаа** мөр үүсгэж чадна. Тиймээс:

| Эрсдэл                     | Хамгаалалт                                                                                  |
| -------------------------- | ------------------------------------------------------------------------------------------- |
| Спам, ботоор мянган хүсэлт | `RateLimitService` — IP-гээр цагт 5, өдөрт 20                                               |
| Давхардсан бүртгэл         | `registrationNumber` дээр `@@unique` (устгаагүй мөрүүдийн дунд)                             |
| Хуурамч цэцэрлэг           | **Админы шалгалт заавал** — алхам 3-гүйгээр `Kindergarten` үүсэхгүй                         |
| Хувийн мэдээлэл алдагдах   | Маягт нь **хүүхдийн ямар ч мэдээлэл асуухгүй**. Зөвхөн байгууллага, эрхлэгчийн холбоо барих |
| Хүсэлтийн жагсаалт задрах  | Уншихад `isSuperAdmin` шаардана — өөрийн хүсэлтээ ч уншиж болохгүй                          |

★ **Хүсэлт нь цэцэрлэг биш.** `KindergartenApplication` бол тусдаа хүснэгт.
`Kindergarten` мөр нь **зөвхөн алхам 3-ын дараа** үүснэ. Хэрэв нээлттэй маягт
шууд `Kindergarten` үүсгэдэг байсан бол тэр нь олон түрээслэгчийн үндсэн
хүснэгтэд нэвтрэлтгүй бичих эрх өгнө — энэ системд байж болох хамгийн муу
гадаргуу.

★★ **404, 403 биш.** Хүсэлтийн дугаараар хандахад superadmin биш хүн 404 авна
(§1.7-ийн зарчим). Гэхдээ хүүхдийн өгөгдөл биш тул §1.7-ийн албан ёсны хамрах
хүрээнд ороогүй — ижил зарчмаар хийж байгаа нь тууштай байдлын үүднээс.

## 2. Өгөгдлийн загвар

### `KindergartenApplication`

Зурган дээрх «Байгууллагын мэдээлэл» маягтын талбарууд:

| Талбар                                     | Төрөл        | Тайлбар                         |
| ------------------------------------------ | ------------ | ------------------------------- |
| `kindergartenName`                         | text         | Цэцэрлэгийн нэр                 |
| `registrationNumber`                       | text, unique | Регистрийн дугаар               |
| `address`                                  | text         | Хаяг                            |
| `directorName`                             | text         | Эрхлэгчийн нэр                  |
| `phone`                                    | text         | Утасны дугаар                   |
| `email`                                    | text         | И-мэйл хаяг                     |
| `childCount`                               | int          | Хүүхдийн тоо — тарифын суурь    |
| `status`                                   | enum         | `PENDING · APPROVED · REJECTED` |
| `reviewedById`, `reviewedAt`, `reviewNote` |              | Алхам 3-ын ул мөр               |
| `kindergartenId`                           | uuid?        | Алхам 3-т үүссэн түрээслэгч     |

★ `registrationNumber` дээрх `@@unique` нь **устгаагүй мөрүүдийн дунд** —
татгалзсан хүсэлт дахин илгээхэд саад болох ёсгүй. Prisma-д хэсэгчилсэн индекс
байхгүй тул миграцид гараар: `CREATE UNIQUE INDEX … WHERE "deletedAt" IS NULL`.

### `Contract`

| Талбар                                          | Тайлбар                                           |
| ----------------------------------------------- | ------------------------------------------------- |
| `number`                                        | `NK-2026-000123` — жилээр дараалсан, unique       |
| `version`                                       | Зурган дээрх «PDF version: v1.0»                  |
| `status`                                        | `PENDING_SIGNATURE · SIGNED · ACTIVE · CANCELLED` |
| `childCount`, `annualFee`, `perChildMonthlyFee` | **Үүсгэх мөчид хөлдөөсөн**                        |
| `startsOn`, `endsOn`                            | Хугацаа                                           |
| `pdfMediaFileId`                                | Алхам 4-ийн гаралт                                |
| `signedMediaFileId`                             | Алхам 7 — 2-р ээлж                                |

★★★ **Үнэ хөлдөнө, лавлагаагаар татагдахгүй.** Гэрээ бол хоёр талын хооронд
гарын үсэг зурагдсан баримт. Хэрэв дүнг тарифын хүснэгтээс уншдаг байвал тариф
өөрчлөгдөх өдөр **өнгөрсөн бүх гэрээний агуулга чимээгүй өөрчлөгдөнө** —
нэгэнт хэвлэгдэж, тамга дарагдсан цаастай зөрөх болно. Энэ нь `FundingRule`-ийн
хувь засагдахгүй байхтай яг ижил шалтгаан (`нэмэлт.md` §4).

★★ **Дүн `Decimal`, хэзээ ч `Float` биш** — §2.2. Репозиторын гадна `decimal.js`.

## 3. Алхам бүр яаж хийгдэх вэ

### Алхам 1–2 — нээлттэй маягт

```
POST /v1/applications            @Public(), rate-limited
```

Хариу нь **хүсэлтийн дугаар ба и-мэйл баталгаажуулалт**, өөр юу ч биш. Хэрэв
регистрийн дугаар давхардсан бол хариу нь ялгагдахгүй байх ёстой — эс бөгөөс
маягт нь «энэ РД бүртгэлтэй юу» гэсэн асуулт хариулах хэрэгсэл болно.

### Алхам 3 — админы шалгалт

```
GET   /v1/platform/applications           superadmin
POST  /v1/platform/applications/:id/approve
POST  /v1/platform/applications/:id/reject
```

Батламжлах гүйлгээ нэг transaction дотор:

1. `Kindergarten` үүсгэнэ
2. **Эрхлэгчийн `User` + `ADMIN` `Membership` + урилгын токен** үүсгэнэ
3. `Application.status = APPROVED`, `kindergartenId` холбоно
4. `Contract` үүсгэнэ — дугаар олгож, үнийг хөлдөөнө
5. `AuditLog` бичнэ

★★★ **Алхам 2 нь 2026-09-02-нд нэмэгдсэн, засвар байсан.** Эхний хувилбар нь
зөвхөн `Kindergarten` үүсгэдэг байсан тул **нэвтрэх хүнгүй цэцэрлэг** үлддэг
байв — урсгал алхам 3 дээр мухардана. API-аас энэ нь харагдахгүй: бүх endpoint
зөв хариулдаг, зүгээр л гишүүнгүй цэцэрлэгийн тухай.

`POST /platform/kindergartens` (хуучин шууд зам) нь эхнээсээ админ болон
урилгыг хамт үүсгэдэг байсан. Одоо хоёр зам «цэцэрлэг оршин байна» гэдгийг ижил
утгаар ойлгож байна.

☆ **Хоёр зам байгаа нь зориуд.** Хүсэлтийн зам нь цэцэрлэг өөрөө бидэн рүү
хандахад; шууд зам нь оператор уулзалт дээр өөрөө бүртгэхэд. Хоёулаа
`Kindergarten` + `ADMIN` + урилга үүсгэнэ; ялгаа нь зөвхөн шууд зам гэрээ
үүсгэдэггүйд байна. Хэрэв гуравдахь зам нэмэгдэх бол `createWithAdmin`-ы биеийг
задлан гаргах хэрэгтэй, дахин хуулах биш.

★ **Дараалалд PDF-ийг transaction-ы ДАРАА нэмнэ** — §3.5. Transaction дотор
нэмбэл worker нь мөр харагдахаас өмнө эхэлнэ.

### Алхам 4 — PDF

`ReportJob`-ийн одоо байгаа дэд бүтцийг ашиглана: BullMQ, Chromium,
кириллийн фонт аль хэдийн суусан. Шинэ `ReportType.CONTRACT`.

★ `FINANCE_REPORT`-той адил **`childId` байхгүй** — гэрээнд хүүхдийн мэдээлэл
байхгүй тул `canAccessChild`-аар хамгаалагдсан татах зам үүнийг хэзээ ч
үйлчлэхгүй.

## 4. 2-р ээлжид үлдэх зүйлс (алхам 5–8)

- Гэрээг татах — `/media/:id` дамжуулан, presigned URL (§1.4)
- Скан хуулах — `MediaPurpose.CONTRACT_SIGNED`, MIME агуулгаас нь тодорхойлно (§1.6)
- Идэвхжүүлэх — `Contract.status = ACTIVE`, `AuditLog`

★ **Цахим гарын үсэг энд байхгүй, зориуд.** RFP §20-оор тэр нь IV үе шат
(CLAUDE.md §7-д «electronic signature» гэж жагсаагдсан). Энэ урсгал нь цаасан
дээрх гарын үсэг, тамгыг скан хийж хадгалдаг — өөр зүйл, өнөөгийн хамрах
хүрээнд байгаа.
