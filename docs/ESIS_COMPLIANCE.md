# ESIS_COMPLIANCE.md — А/261 шаардлагын өөрийн үнэлгээ

**Зорилго:** Боловсролын сайдын 2024 оны А/261 тушаалаар батлагдсан шаардлагын
дагуу NomadKids системийн төлөвийг мөр мөрөөр нь тулгасан үнэлгээ. Энэ бол
БМТТ-д токен хүсэхийн өмнө бидний өөрсдөө хийсэн шалгалт — гуравдагч этгээдийн
гэрчилгээ биш.

**Төлөв:** 2026-08-31-ны байдлаар. Кодын лавлагаа тухайн өдрийн `main` салааны
байдлыг заана.

> **Хэлний тухай.** CLAUDE.md-ийн дүрмээр баримт бичиг англиар бичигдэнэ. Энэ
> файл түүний **зориудын үл хамаарах тохиолдол**: шаардлагын бичвэрийг
> **үг үсэгчлэн монголоор** хуулсан бөгөөд ингэснээр яамны шалгагч өөрийн
> хувьтай мөр мөрөөр нь тулгаж чадна. Орчуулсан бичвэр тулгалтыг боломжгүй
> болгоно. Кодын нэр, файлын зам англиар хэвээр.

## 1. Хоёр баримт хэрхэн хоорондоо холбогдох вэ

Энэ хоёр тушаал тусдаа биш, гинжин холбоотой:

| Баримт                                                                       | Огноо, дугаар     | Юу хүчингүй болгосон                          | Эх хувь                                               |
| ---------------------------------------------------------------------------- | ----------------- | --------------------------------------------- | ----------------------------------------------------- |
| **Журам** — "Боловсролын цахим мэдээллийн сан бүрдүүлэх, ажиллуулах журам"   | 2025-09-25, А/465 | Боловсролын сайдын 2024 оны А/260 тушаал      | `docs/reference/legal/A465-2025-09-25-jouram.pdf`     |
| **Шаардлага** — ерөнхий шаардлага, тусгай шаардлага, санхүүжилтийн эх үүсвэр | 2024-12-19, А/261 | БШУ-ны сайдын 2022 оны 111, 370 дугаар тушаал | `docs/reference/legal/A261-2024-12-19-shaardlaga.pdf` |
| **Заавар** — БМТТ, токен авах заавар                                         | огноогүй          | —                                             | `docs/reference/legal/BMTT-token-guide.pdf`           |

Гинжин холбоо нь:

1. **Журам §3.4** — систем хөгжүүлэгч яаманд дөрвөн баримт бүрдүүлж хүсэлт
   гаргана (доор §5.1).
2. **Журам §3.5** — яам мэдээлэл солилцох гэрээ байгуулна.
3. **Журам §3.6** — хөгжүүлэгчийн систем **ерөнхий болон тусгай шаардлагыг**
   хангасан байх ёстой. Энэ нь яг **А/261**.
4. **Журам §3.7** — БМТТ нь §3.6-г хангасан тохиолдолд **хөгжүүлэгчид зөвхөн
   нэг токен** олгож мэдээлэл солилцоно.

★ Тиймээс "шаардлагын дагуу болгох" ба "холбогдоход бэлэн болгох" гэдэг нь хоёр
ажил биш, **нэг ажил**: А/261-ийн хангалт нь токены урьдчилсан нөхцөл, токен нь
холболт өөрөө. Өнөөдөр үзүүлж болох зүйл нь энэ өөрийн үнэлгээ, мөн залгагдсан
хэрнээ тохиргоогүй байгаа интеграцийн хил (§4).

★★ Нэг зөрчлийг тэмдэглэе: А/261 нь өөрийн үндэслэлдээ **А/260**-ыг иш татдаг
бөгөөд түүнийг А/465 хүчингүй болгосон. Гэвч А/465 нь А/261-ийг хүчингүй
болгоогүй тул шаардлага хүчинтэй хэвээр, зөвхөн иш татсан үндэслэл нь хуучирсан.
Хүсэлт илгээхдээ энэ талаар тодруулга асуух нь зүйтэй (§6.2).

## 2. Тэмдэглэгээ

| Тэмдэг | Утга                                                |
| ------ | --------------------------------------------------- |
| ✅     | Хангасан — нотолгоо нь код эсвэл баримт бичгийн зам |
| ◐      | Хэсэгчилсэн — юу дутсаныг мөрөнд нь бичсэн          |
| ✗      | Хангаагүй                                           |
| ⊘      | Хамааралгүй — шалтгааныг нь бичсэн                  |

Багана `З/Ө`: **З** = зайлшгүй шаардлагатай, **Ө** = зөвлөмжийн шинжтэй.
А/261-ийн бичсэнээр зайлшгүй шаардлагыг **заавал** хангах, зөвлөмжийн шинжтэйг
**заавал хөгжүүлж, нэвтрүүлэхгүй байж болно**.

## 4. Холболтод бэлэн эсэхийг хэрхэн үзүүлэх вэ

Ерөнхий шаардлага #29 бол токены гол шалгуур. Түүнийг **үзэж болно**:

```
GET /v1/health/readiness      (зөвхөн ADMIN эрхээр)
```

Хариунд `esis` хэсэг байна:

```json
"esis": {
  "configured": false,
  "baseUrl": "",
  "institutionId": "",
  "hasToken": false
}
```

Энэ нь яг дараах зүйлийг хэлж байна: **холболтын хил залгагдсан, гэхдээ
итгэмжлэл хараахан суугаагүй.** Токен ирээд `ESIS_BASE_URL`, `ESIS_TOKEN`,
`ESIS_INSTITUTION_ID` гурвыг тохируулмагц ижил дуудлага `configured: true`,
`hasToken: true` буцаана — код өөрчлөх шаардлагагүй.

- `apps/api/src/health/health.controller.ts` — хариултыг угсрах газар
- `apps/api/test/health.test.ts` — токен хариунд гарахгүйг батлах сорил
- `.env.example` §ESIS — тохируулах гурван хувьсагч

★ **Энд амьд дуудлага байхгүй нь зориуд.** ESIS рүү жинхэнэ хүсэлт илгээж
шалгах гэвэл ямар endpoint рүү илгээхээ сонгох хэрэгтэй, харин баримт бичиг
ирэхээс өмнө сонгох нь таамаг болно. `esis.service.ts` домэйн методгүй байгаагийн
шалтгаан яг энэ — таамгаар бичсэн endpoint дээр дэлгэц баригдмагц таамаг тархана.

★★ **Токен яаж ирдэг вэ** (БМТТ-ийн "Мэдээлэл солилцох систем дээр TOKEN авах
заавар"): гэрээ байгуулсны дараа систем нэвтрэх нэр, нууц үгийг **автоматаар
үүсгэж** байгууллагын цахим шуудан руу `info.edu.mn`-ээс илгээнэ.
`developerv2.esis.edu.mn` рүү нэвтрэн ACCESS_TOKEN-ыг харна (тэнд
`ENTRY_SOURCE_ID` мөн харагдана). Өөрөөр хэлбэл **урт хугацааны нэг токен**,
`login` урсгал биш — `ESIS_REQUEST.md` Хавсралт 4-ийн асуултын нэг нь ингэж
хаагдсан.

## 8. Хавсралт 3 — Санхүүжилтийн эх үүсвэр

А/261-ийн гуравдугаар хавсралт нь СӨБ-ын салбарын дэд систем бүрийн
санхүүжилтийн эх үүсвэрийг тогтоосон. Бүх найман дэд систем **"цахим
хэрэглээний зардал"**-аар, үүнээс эцэг эх, асран хамгаалагч нь нэмж
**эцэг эхийн портал** ба **хоол үйлдвэрлэлийн удирдлага** хоёрыг санхүүжүүлнэ.

Энэ нь ерөнхий шаардлага #32-той шууд холбоотой: төрийн болон донорын
санхүүжилтээр хийгдээгүй тул эцсийн хэрэглэгчээс төлбөр авахыг хориглох заалт
хамаарахгүй.
