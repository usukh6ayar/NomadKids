# MIGRATION_PLAN.md — from the Django reference system

**Status:** design only.

## 1. There is no production data to migrate

Verified in the reference repository:

- **No production deployment has happened.** `ROADMAP.md` lists deployment as
  outstanding; `docs/SERVER-SETUP.md` describes a server that was never cut over.
- The only database artefact is **one development dump**,
  `backups/kinder-20260810T082519Z.dump`, 359 KB, dated 2026-08-10.
- Demo content is generated by a management command, `seed_demo.py`.

**Therefore this document is a schema classification, not an ETL plan.** The new
system starts with an empty database and a seed script. Writing a data pipeline
for data that does not exist would be a day spent on nothing.

**If that changes** — if the Django system is put in front of real users before
the new one ships — this document must be revisited, and §6 becomes real work.

## 3. Points needing care

The brief singles these out. Each is a place where a naive port loses a
guarantee.

| Concern                           | What must survive                                                                                                                                                                                                                  |
| --------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Enrollment history**            | Authorization derives the kindergarten set from _all_ enrollments, not the current one. Rows are ended, never deleted. The no-enrollment fallback to `Child.kindergartenId` is kept deliberately — [SECURITY.md](SECURITY.md) §5.2 |
| **Guardianship history**          | `canView = false` revokes access while preserving the record. Never delete a guardianship to revoke                                                                                                                                |
| **GroupTeacher soft deletes**     | Revocation is `endedOn`, not deletion, so historical attribution survives. Two reference tests depend on it                                                                                                                        |
| **Observation visibility**        | `visibleToParents` defaults to **false**. A migration that defaults it true would disclose every private teaching note                                                                                                             |
| **Assessment domains and levels** | Configuration rows with `kindergartenId = NULL` are system defaults, shared and not editable by a kindergarten admin. The seed must create them; the override mechanism must exist from day one                                    |
| **Audit logs**                    | Append-only. No `updatedAt`, no soft delete, `actorLabel` denormalised so a deleted user's actions stay attributable                                                                                                               |
| **Media object keys**             | `storageKey` is a random UUID path, never derived from a name or id. If real files ever move, keys are **copied verbatim** — regenerating them breaks every stored reference                                                       |
| **Report jobs**                   | Historical jobs are not migrated; their outputs expire. New system starts with an empty queue                                                                                                                                      |

## 4. Seed data

The seed script must produce a working system, not a demo:

1. System `DevelopmentDomain` rows (`kindergartenId = NULL`) — the five domains.
2. System `AssessmentLevel` rows — the four levels, values 1–4.
3. System `ObservationType` rows.
4. One superadmin.

Demo content — a kindergarten, groups, children, guardians, observations — sits
behind a separate `seed:demo` command and never runs in production.

The domain, level and type names come from the reference system's own seed so
the client sees the vocabulary they approved.

---

## 5. Cutover

Since nothing is live, "cutover" is a launch:

1. Provision Postgres, Redis, R2.
2. `prisma migrate deploy`, then `seed`.
3. Create the real kindergarten, groups and staff through the admin UI.
4. Import children — **manually or by a one-off CSV script**, from whatever the
   client actually has today (spreadsheets, most likely). Not from Django.
5. Invite guardians.

The reference system stays in the repository, read-only, as the behavioural
specification. It is not run in parallel and not kept in sync.

---

## 6. If production data appears

Then, and only then:

1. `pg_dump` the Django database.
2. Map tables per §2, in FK order: `Kindergarten → SchoolYear → Group → User →
Membership → GroupTeacher → Child → Guardianship → Enrollment → config →
Observation → Assessment → Media → Notification → AuditLog`.
3. Integer PKs become UUIDs — carry a `legacyId` column through the import so
   FKs can be rewired, then drop it.
4. Copy R2/MinIO objects **key for key**.
5. Reconcile: row counts per table, plus a spot check that a sample of children
   resolve to the same authorized users in both systems.
6. Keep the Django dump for 90 days.

This is roughly two days of work and is **not** in the current estimate.
