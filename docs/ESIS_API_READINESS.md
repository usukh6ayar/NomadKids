# ESIS v2 API бэлэн байдлын матриц

**Шалгасан огноо:** 2026-09-08

**Албан ёсны эх:** <https://developerv2.esis.edu.mn/api/structure>

**Hub:** `https://hubv2.esis.edu.mn`

Developer portal-ийн public catalog-д нийт **198 сервис** байна: 119 `GET`,
79 `POST`. NomadKids бүх сервисийг хүсэхгүй. А/261-ийн мэдээлэл солилцоо болон
СӨБ-ын шаардлагыг хангахад шууд хэрэгтэй **17 сервисийг** хамгийн бага эрхийн
зарчмаар сонгож backend adapter-т оруулсан.

Portal-ийн 2026-03-31-ний мэдэгдэл v1 сервисүүдийг 2026-04-01-нээс хааж эхлэхийг
зарласан. Иймээс энэ матриц зөвхөн `/hub/v2/` зам ашиглана.

### 1.1 C4 — эхний бодит тулгалт, 2026-09-14

Яамны өөрийн зөвшөөрөгдсөн сервисийн жагсаалт (`apis-granted.xlsx`, 84 мөр,
API_ID + method + URL) болон **амьд хариунуудтай** каталогийг тулгав.

| Шалгасан зүйл                               | Дүн                                                             |
| ------------------------------------------- | --------------------------------------------------------------- |
| Холбогдсон 40 сервисийн зам ба method       | **40/40 таарсан** — зөрүүгүй                                     |
| Хүсэлтийн бүртгэл (`esis.requests.ts`)      | 84 зөвшөөрөгдсөн ID бүгд байна; илүү 13 нь PENDING/CANCELLED     |
| Уншигчийн schema-г амьд хариутай тулгасан   | **36-аас 9 нь буруу** — 2 нь бүр алдаа өгдөг, 7 нь утгыг хаядаг  |
| Хоосон хариу (`203`)                        | 3 өөр хэлбэр: `RESULT: ""`, `RESULT: []`, `RESULT` огт байхгүй   |

Эндээс гарсан засварууд:

- `esisListParser` хоосон хариуг «гэрээ зөрчсөн» биш «мэдээлэл алга» гэж
  уншина. Өмнө нь `groupsNextYear` энэ шалтгаанаар амьд орчинд унаж байсан.
- `rooms` (`roomId` → `facilityId`) ба `academicOrg`
  (`academicOrgId` → `subjectDepartmentId`) шаардлагатай талбар нь буруу байсан
  тул бүтэн сервис `invalid_response` өгдөг байв.
- `teacherAcademicOrg`, `teacherMovements`, `studentCondition`,
  `studentStatistics`, `programs`, `subjectAreas`, `students` — зохиосон
  талбарууд нь бүгд nullable байсан тул parse хийгдээд утга нь чимээгүй
  хаягддаг байлаа. Дэлгэц хоосон багана зурж, «энэ байгууллагад мэдээлэл алга»
  мэт харагдана.
- `studentCheck` бол объект биш, `"true"` гэсэн ганц утга. `studentContacts` бол
  бүх бүртгэлийнх биш, **нэг хүүхдийн** лавлагаа.
- `fieldSource` дээр гурав дахь утга `LIVE` нэмэгдсэн: `PORTAL` = яам баримтжуулсан,
  `LIVE` = яам **илгээсэн**, `ADAPTER` = хоёуланг нь шалгаагүй.

### 1.1.2 Гэрээ нь тодорхойгүй сервисүүд

Зургаан уншигч (`97`, `98`, `96`, `94`, `93`, `194`) институт 42778-ийн бүх 83
хүүхдэд `203` буцаадаг тул **гаралтын талбарууд нь хэзээ ч харагдаагүй**.

Тэдгээрт зохиосон талбарын жагсаалт бичээгүй. Оронд нь дамжуулах схем
(`esisDiscoveredSchema`) ашиглаж, дэлгэц нь **эхний бодит хариунаас** баганаа
уншина (`ESIS_DISCOVERED_SHAPE`, `esisFieldsFor`). Ингэснээр §1.1-д бичсэн
«зохиосон талбар» алдааг давтахгүй бөгөөд бодит бичлэг гарч ирэхэд ЭСИС-ийн
өөрийнх нь нэрсийг утгатай нь харна.

★ Дамжуулах схем дээр «нэрлээгүй учраас авахгүй» гэдэг хамгаалалт ажиллахгүй
тул `civilId`, `personRegNumber`, нууц үгсийг **кодоор** таслана
(`ESIS_REFUSED_FIELDS`), мөн үүнийг тестээр баталгаажуулсан.

### 1.1.4 Хүүхэд тус бүрийн уншилтын эрх — 2026-09-15

`assertReadable` нь хоёр л зүйл шалгадаг байв: дуудагч энэ түрээслэгчийн гишүүн
үү, түүний эрх энэ сервист хүрэх үү. **Аль нь ч хүүхдийн тухай биш.**

Хүүхэд тус бүрийн ESIS сервис бүр `personId`-аар хаяглагддаг бөгөөд `students`
нь бүх roster-ын дугаарыг ямар ч багшид өгдөг. Тиймээс **1-р бүлгийн багш
2-р бүлгийн хүүхдийн харшил, хөгжлийн бэрхшээл, хэмжилтийг уншиж чадна**
байсан — CLAUDE.md §4.1-ийн эхний тохиолдол.

Энэ нь 2026-09-10-нд нэмэгдсэн `studentStatistics`, `studentCondition`,
`studentCheck`-д аль хэдийн байсан цоорхой; 2026-09-15-нд эрүүл мэндийн 11
сервис нэмэгдэхэд цар хүрээ нь эрс өргөжсөн тул хаав.

**Яагаад шууд засагдаагүй вэ:** `Child`-д ESIS `personId` багана байгаагүй тул
`canAccessChild`-ыг `personId`-д хэрэглэх зам огт байхгүй байв.

| Юу нэмэгдсэн | Хаана |
| --- | --- |
| `Child.esisPersonId` багана, `(kindergartenId, esisPersonId)` unique | `20260915090000_child_esis_person_id` |
| `personId` → `Child` тайлагч | `EsisRepository.findChildIdByEsisPersonId` |
| Эрхийн хаалт | `EsisAdminService.assertCanReadEsisChild` |
| Тулгалтыг санах | `AttendanceRepository.rememberEsisPersonIds` |

**Дүрэм:**

- **ADMIN чөлөөлөгдөнө.** `isAdminOver` нь тухайн цэцэрлэгийн бүх хүүхдэд
  зөвшөөрдөг тул хаалт «тийм»-ээс өөр хариулт өгөх боломжгүй. Ажиллуулбал
  нэмэлт query болох ба, илүү дор нь, ESIS дугаар нь тулгагдаагүй хүүхдийг
  admin-д хориглох болно — дүрэм өөрөө зөвшөөрч байгаа хандалтыг татгалзана.
- **Тулгагдаагүй бол татгалзана.** `esisPersonId` нь зөвхөн бүтээгдэхүүн амьд
  roster-тай нэр, төрсөн огноогоор тулгалтыг баталсан газарт бичигддэг
  (`resolveAttendanceDrafts`). Дугааргүй хүүхдийг хэнийх болохыг тогтоох
  боломжгүй, «хэнийх нь мэдэхгүй» гэдэг нь харуулах шалтгаан биш.
- **403 биш 404** (§1.7) — дуудагч тухайн дугаар байгаа эсэхийг ч мэдэхгүй.

Мандат 6 тест `test/esis-admin.test.ts`-д, бодит маршрутаар HTTP-ээр.

### 1.2 Олон байгууллага — token хэрхэн хуваагддаг

2026-09-14-нд хэмжсэн: `organization/info` дээр `42778` → `200`, харин `40284`,
`42779`, `42780`, `1` → бүгд `403 «Таны компанид энэ institutionId дээр эрх
байхгүй байна»`.

Өөрөөр хэлбэл token нь **олгогдсон institution-уудын багц** авч явдаг бөгөөд
түүнээс гадуурх ID-г яам өөрөө татгалзана. Хоёр дүгнэлт:

1. Түрээслэгч хоорондын тусгаарлалтыг зөвхөн
   `Kindergarten.esisInstitutionId` барьж байгаа юм биш. Энэ бол эхний шалгалт,
   яам нь хоёр дахь нь — мөн бидний хяналтаас гадуурх учир санамсаргүй
   эвдэгдэхгүй.
2. Шинэ цэцэрлэг нэмэх нь **бичиг баримтын** алхам, кодын биш: яам тухайн
   institution-ыг энэ данс дээр нэмнэ, дараа нь superadmin баганыг тохируулна.

«Таны **компанид**» гэсэн үг нь данс нь компани бөгөөд institution-ууд түүнд
хавсрагддагийг хэлж байна. Хэрэв яам ирээдүйд цэцэрлэг бүрээс өөрийн developer
данс шаардвал ганц `ESIS_TOKEN` орчны хувьсагч хүрэлцэхгүй болж, credential нь
tenant тус бүрийн шифрлэсэн хадгалалт руу шилжинэ.

Ингэснээр `/v1/platform/kindergartens/:id/esis` нь C3-ыг `READY`, blocker-ыг
хоосон гэж мэдээлдэг болсон.

Энэ мөрийг засаж байгаа шалтгаан нь CLAUDE.md §7 өөрийгөө дахин дахин зассан
шалтгаантай нэг: кодын бодит байдалтай зөрчилдсөн баримтыг хүн уншихаа болино.

## 2. Сонгосон endpoint ба ашиглах газар

Бүх замын өмнө default-аар `https://hubv2.esis.edu.mn` орно. `institutionId`-г
backend тухайн tenant-ийн `Kindergarten.esisInstitutionId` mapping-аас нэмнэ.
Ингэснээр нэг provider token олон гэрээт цэцэрлэгийг tenant-safe байдлаар
үйлчилнэ.

| API                        | Method ба зам                                                        | NomadKids-д ашиглах газар                       | Одоо  |
| -------------------------- | -------------------------------------------------------------------- | ----------------------------------------------- | ----- |
| 100004874669792 / `api-22` | `GET /svc/api/hub/v2/group/list/attendance/:studentGroupId/:dayDate` | Илгээсний дараах тулгалт, зөрүүний хяналт       | C1+C2 |

`v3` нь `institutionId`, `studentGroupId`, `dayDate`, мөн хүүхэд бүрийн
`personId`, `attendReasonCode`, `tardyMinutes`, `attendReasonList` авна. Манай
одоогийн attendance status-ыг ESIS-ийн reason code-той тулгах хүснэгт catalog-д
байхгүй тул C5 хийхээс өмнө token-той lookup/test шаардлагатай.

`/attendance/daily` дээр бүрэн бүртгэгдсэн бүлэг-өдрийг сонгоход
`POST /kindergartens/:id/attendance/daily/esis-preview` нь API-000269-ийн
илгээх body-г хүүхэд бүрийн мөрөөр бэлтгэж дэлгэцэд харуулна. Portal-ийн
гаралтын тайлбарт байгаа кодоор demo mapping нь `PRESENT`/`HALF_DAY → PRESENT`,
`EXCUSED → EXCUSED`, `SICK → SICK`, `ABSENT → UNEXCUSED`. Тодорхой ESIS
шалтгаангүй `OTHER`-ийг таамаглахгүй, илгээхийн өмнө засах алдаа болгоно.
Token байхгүй үед preview алдаа буцаана — 2026-09-14 хүртэл `demo: true`
payload үзүүлдэг байсан бөгөөд тэр нь зохиомол `institutionId`, hash-аас
гаргасан `studentGroupId`, `personId` агуулдаг байв: багш бүрэн бөгөөд
итгэмээр хүсэлт хардаг ч ЯАМ-д танигдахгүй дугаартай байлаа. Token байгаа
үед API `groups` болон `groupStudents`-ийг бодитоор дуудаж, бүлгийг нэрээр,
хүүхдийг овог нэр + төрсөн огноогоор цорын ганц тохирсон үед ESIS-ийн
`studentGroupId`, `personId`-г payload-д тавина. Олдоогүй эсвэл давхардсан
тохиолдолд буруу ID таахгүй, илгээлтийг зогсооно. `Илгээх` нь API-000269 POST
амжилттай болсны дараа л local `AttendanceSubmission` хадгална.

бөгөөд ямар баримтаар татгалзсаныг нэрлэнэ.

нэрсийн олонлог зохих zod схемийн түлхүүрүүдтэй яг тэнцүү байх ёстой.

## 4. Эрх олгогдсон ч холбоогүй сервисүүд

★ **Энэ хэсгийн нэр ба үндэслэл 2026-09-14-нд өөрчлөгдсөн.** Өмнө нь
«Одоогоор зориуд **холбоогүй**» гэж нэрлээд эхний мөр нь «эмчийн тусгай эрх …
шийдэгдсэний дараа л **scope хүснэ**» гэж байв. Портал дээрх «Ашиглах
боломжтой сервисүүд» жагсаалт нь **84 сервисийг зөвшөөрөгдсөн** гэж харуулж
байгаа бөгөөд түүний дотор эрүүл мэнд, вакцин, харшил, хөгжлийн бэрхшээл бүгд
байна. Scope нь хүлээгдэж байгаа зүйл биш — **аль хэдийн олгогдсон**. Хүлээж
буй зүйл нь бидний тал: зорилгын зөвшөөрөл, retention бодлого, эмчийн эрхийн
загвар.

Ялгаа нь чухал: «эрх алга» гэдэг нь гадаад саад, «эрхтэй ч холбоогүй» гэдэг нь
бидний шийдвэр. Хоёрдугаарыг нь эхнийх мэтээр бичих нь БМТТ-г буруутай мэт
харуулна.

Кодод **39 сервис** холбогдсон, бүгд зөвшөөрөгдсөн (apiId, method, зам тулгасан
— зөрүүгүй). Үлдсэн **45** нь дараах шалтгаанаар:

- **Эрүүл мэнд, вакцин, харшил, хөгжлийн бэрхшээл, мэс засал, осол гэмтэл,
  өсөлт хөгжил, эрт илрүүлэг** (apiId 62-64, 75-82, 93-99, 108-109, 190,
  194-195): **эрхтэй**. Зорилгын зөвшөөрөл, retention хугацаа, эмчийн тусгай
  эрхийн загвар шийдэгдээгүй тул холбоогүй. NomadKids-д `growth_measurements`,
  `vaccination_records`, `allergy_records`, `safety_incidents`,
  `special_need_records` хүснэгтүүд аль хэдийн байгаа тул энэ нь **дараагийн
  шатны хамгийн том боломж**.
- **Анги бүлэг үүсгэх/засах/устгах POST** (150, 152, 162): эрхтэй. СӨБ-д буруу
  өгөгдөл үүсгэх эрсдэл нь unchanged — бүлэг устгах бол буцаах боломжгүй.
- **Мэргэшлийн зэрэг** (119, 165, 167, 170): эрхтэй. Багшийн хөгжлийн модуль
  NomadKids-д байхгүй.
- **Гэр бүл, өрхийн мэдээлэл** (73, 87): эрхтэй ч `ESIS_REQUEST.md` §1.3-аар
  зориуд хүсээгүй хэвээр — §1.1 (b)-ийн шалтгаан хүчинтэй.
- **Хоолны маягт 1/2 хадгалах** (129, 131): эрхтэй. **Унших** тал нь (130, 132)
  холбогдсон; бичих нь батлагдсан маягтын mapping хийгдээгүй тул үлдсэн.
- **Дүн, шалгалт, сурах бичиг, дүрэмт хувцас, дотуур байр**: СӨБ-ын
  NomadKids-ийн зорилгод хамаарахгүй.

## 5. C3-C5 руу шилжих checklist

1. `ESIS_REQUEST.md`-ийн API ID жагсаалтаар авах/өгөх scope батлуулах.
2. Гэрээ байгуулж `ACCESS_TOKEN`, `ENTRY_SOURCE_ID` авах.
3. Portal-ийн хэрэглэгчийн хуудсаас 17 API-ийн access status-ыг export/screenshot
   хийж change record-д хавсаргах.
4. ESIS test орчинд нэг цэцэрлэгээр GET contract test ажиллуулах.
5. Ирцийн code mapping, POST idempotency/error contract-ыг test response-оор
   батлах.
6. Урт хугацааны import-д external ID + field conflict хадгалалт, BullMQ
   dead-letter, operator approve UI нэмэх. Attendance нь одоогоор live roster-оос
   deterministic тулгалт хийдэг тул token ирмэгц ажиллана.
7. Production-д эхлээд read-only sync, дараа нь нэг цэцэрлэгийн attendance POST,
   эцэст нь шаталсан rollout хийх.

2026-09-08-ны хэрэгжилтээр `sync run/result`, tenant-safe mapping, operator
read-only preview, safe GET retry, live profile/student output, attendance live
resolve + POST хийгдсэн. Bulk import-ийн persisted external ID, field-level
conflict, approve/import, dead-letter queue нь дараагийн operational шатанд үлдсэн.
