# ESIS_REQUEST.md — БШУЯ-д илгээх мэдээлэл солилцох хүсэлтийн ноорог

**Зорилго:** "Мэдээлэл солилцох гэрээ"-ний хавсралт болох талбарын жагсаалтыг
урьдчилан бэлдэх. Гэрээний хавсралт нь практик дээр манай API-гийн scope болно
— тэнд бичигдээгүй талбар хэзээ ч ирэхгүй, харин илүү бичсэн талбар нь хэрэггүй
хувийн мэдээллийг татах үүрэг болж хувирна.

**Төлөв:** ноорог. Гарын үсэг зурах эрх бүхий хүн шалгаж, компанийн албан бланк
дээр буулгана. `[ ]` доторх зүйлсийг бөглөнө.

> ★ ESIS v2-ийн public catalog-ийг 2026-09-07-нд шалгаж, сонгосон endpoint-уудыг
> `ESIS_API_READINESS.md`-д API ID-тай нь бүртгэж, backend schema/domain method
> нэмсэн. Энэ файл одоо token scope батлуулах албан хүсэлтийн эх болно.

> ★★ **Хамтрагч файл: `docs/ESIS_COMPLIANCE.md`.** Энэ файл нь бид **юу хүсэж
> байгааг**, тэр файл нь бид **юуг хангасныг** бичдэг. Журам А/465 §3.6-оор
> хоёр дахь нь эхнийхийн урьдчилсан нөхцөл: шаардлага хангаагүй бол токен
> олгогдохгүй.

1. **Гэрээний шалгуур нь нийтэд нээлттэй байсан** — журмын §3.6 нь хөгжүүлэгчийн
   системийг **А/261-ийн ерөнхий болон тусгай шаардлагад** нийцүүлэхийг
   шаарддаг, §3.7 нь түүнийг хангасан үед л БМТТ **нэг токен** олгоно гэсэн.
   Тиймээс "шаардлагад нийцүүлэх" ба "холбогдоход бэлэн болгох" нь нэг ажил.
   Мөр мөрөөр нь тулгасан үнэлгээ: **`docs/ESIS_COMPLIANCE.md`**.
2. **Хоёр талын солилцоо нь үүрэг** — журмын §3.17 нь анхан шатны бүртгэлийн
   мэдээллийг **бодит цагийн горимоор хүргүүлэхийг** шаарддаг. Энэ ноорог өмнө
   нь "зөвхөн унших" байр суурьтай байсныг доор засав (Хавсралт 1).
3. **Токен нь урт хугацааны нэг түлхүүр** — БМТТ-ийн заавраар гэрээ байгуулсны
   дараа нэвтрэх нэр, нууц үг байгууллагын и-мэйл рүү ирж, `developerv2` дээрээс
   `ACCESS_TOKEN`-ыг харна.

**2026-09-07-нд баталгаажсан нь:** `developerv2.esis.edu.mn/api/structure`
public catalog-оос 198 сервисийн API ID, method, v2 URL, параметр, sample-ийг
авсан. NomadKids-д хэрэгтэй 17 сервис backend adapter-т орсон.

**Хараахан баталгаажаагүй нь:** манай token-д олгох service scope, rate limit,

олгогдсон гэсэн үг биш.

## Хавсралт 1 — Сервис үйлчилгээний нэр /авах, өгөх/

★ **Энэ хэсгийн байр суурь 2026-08-31-нд өөрчлөгдсөн.** Өмнө нь "бүгд зөвхөн
унших, бичих (`POST`) сервис хүсэхгүй" гэж бичигдсэн байв. Тэр бол болгоомжлолын
сонголт байсан бөгөөд журмын эх бичвэрийг уншсаны дараа **журамд нийцэхгүй нь
тогтоогдов**. Гурван заалт нэг зүг заана:

- **Журам §3.17** — хөгжүүлэгч нь анхан шатны бүртгэлийн мэдээллийг **бодит
  цагийн горимоор** мэдээлэл солилцооны системд **хүргүүлнэ**;
- **А/261 Хавсралт 1 #29** — боловсролын салбарын өгөгдлийн сантай холбогдсон
  байх (**өгөх**, авах) — зайлшгүй шаардлага;
- **А/261 Хавсралт 2 §1 #3, #51** — БСМС-ээс татдаг **бөгөөд түүн рүү илгээдэг**
  байх — зайлшгүй шаардлага.

Мөн журмын **§3.4.3** нь хүсэлтэд сервисийг **"/өгөх, авах/"** гэж нэрлэхийг
шууд шаарддаг. Тиймээс хоёр талын солилцоо нь бидний хүсэл биш, **үүрэг**.

Хамгаалалтын зарчим өөрчлөгдөөгүй: хамгийн бага талбар, зорилгын хязгаартай.
Өөрчлөгдсөн нь чиглэл — **өгөх талыг нуухаа больж, ил тодоор жагсаав**.

Дээрх санал нь ESIS-ийн үйлчилгээнд ачаалал үүсгэхгүй, ирцийн өдрийн бүртгэлийг
тухайн өдөрт нь хүргэх тэнцвэр — Хавсралт 4-т асуулт болгон тавьсан.

### 1.0c Өгөхгүй байхыг хүсэж буй зүйлс

Дараах өгөгдлийг **анхан шатны бүртгэл гэж үзэхгүй** тул илгээхгүй байхыг хүсэж
байна:

- хүүхдийн хөгжлийн **ажиглалтын бичвэр**, багшийн тэмдэглэл;
- **зураг, видео** болон бусад медиа файл;
- эрүүл мэнд, харшил, эмийн зөвшөөрөл, ослын бүртгэлийн **дэлгэрэнгүй**;
- эцэг эхтэй солилцсон **мессеж**;
- судалгааны **хувь хүний хариулт**.

★ Эдгээр нь эцэг эхийн зөвшөөрөлтэйгээр, тухайн цэцэрлэгийн сурган хүмүүжүүлэх
зорилгоор цуглуулагдсан мэдээлэл бөгөөд Хүний хувийн мэдээлэл хамгаалах тухай
хуулийн зорилгын хязгаарын зарчмаар өөр зорилгод шилжүүлэхэд тусдаа үндэслэл
шаардлагатай. Хэрэв яам эдгээрийн аль нэгийг шаардах бол **аль заалтын дагуу
болохыг зааж өгөхийг** хүсэж байна — тэр тохиолдолд зөвшөөрлийн бүртгэл,
хадгалах хугацааны бодлогыг тусад нь тохирно.

### 1.1 Талбарын түвшний хүсэлт — хүүхэд (#5)

Хүүхдийн мэдээллийг **зөвхөн дараах талбараар** хүсэж байна:

| Талбар                              | Манай багана           | Тайлбар                                     |
| ----------------------------------- | ---------------------- | ------------------------------------------- |
| Овог                                | `children.lastName`    |                                             |
| Нэр                                 | `children.firstName`   |                                             |
| Төрсөн огноо                        | `children.dateOfBirth` | Насны бүлэг, өсөлтийн жишиг тооцоход        |
| Хүйс                                | `children.sex`         |                                             |
| Бүлэг (ID, нэр)                     | `enrollments.groupId`  |                                             |
| ~~Регистрийн дугаар~~               | `children.nationalId`  | **Хүсэхгүй** — ↓ доорх тэмдэглэгээг үзнэ үү |
| ESIS-ийн дотоод дугаар (`personId`) | _(шинэ хүснэгт)_       | Дахин тулгалтын түлхүүр                     |

★ **Регистрийн дугаар.** Манай схемд `children.nationalId` талбар байдаг бөгөөд
`@@unique([kindergartenId, nationalId])` буюу цэцэрлэг доторх давхардлыг
хориглодог. Гэхдээ ESIS-ээс РД татах эсэх нь **зөвхөн техникийн шийдвэр биш**:
Хүний хувийн мэдээлэл хамгаалах тухай хуулиар хүүхдийн мэдээллийг хууль ёсны
төлөөлөгчийн зөвшөөрөлтэйгээр, зорилгын хязгаартай боловсруулна.

Хоёр хувилбар:

- **(a)** РД-г татаж хадгална — тулгалт хамгийн найдвартай, гэхдээ нэмэлт
  хамгаалалт, зөвшөөрлийн бүртгэл, хадгалах хугацааны бодлого шаардана.
- **(b)** РД-г **огт татахгүй**, `personId`-аар тулгана — хувийн мэдээллийн
  ачаалал хамгийн бага. `personId` нь ESIS-ийн дотоод дугаар бөгөөд бидний
  талд өөрөө утга илэрхийлэхгүй.

**Энэ ноорог (b)-г сонгосон** — хүснэгтэд РД дарагдсан байгаа нь тийм учиртай.
`children.nationalId` талбар схемд байх боловч цэцэрлэг өөрөө гараар оруулах
эрхтэй хэвээр үлдэнэ; ESIS-ээс автоматаар дүүргэхгүй.

(a)-г сонговол хүснэгтийн зураасыг арилгаад, Хавсралт 2-т РД-д хамаарах хадгалах
хугацаа, устгах журмыг нэмэх ёстой. Гэрээний хавсралтаас талбар **хасах** нь
дараа нь **нэмэхээс** хамаагүй хялбар тул эргэлзвэл (b)-гээр эхэл.

★★ **А/261-ийн ерөнхий шаардлага #16-тай зөрчилдөх үү?** Тэр шалгуур нь
"Монгол Улсын иргэний бүртгэлийн дугаар (civil-id)-аар ... таньж, тодорхойлдог
байх"-ыг **зайлшгүй** гэсэн. Зөрчилдөхгүй: `children.nationalId` талбар схемд
байгаа, цэцэрлэг өөрөө бөглөнө, тиймээс систем РД-аар таньж чадна. Хувилбар (b)
нь зөвхөн **ESIS-ээс автоматаар татахгүй** гэсэн үг. Хэрэв БМТТ энэ ялгааг
хүлээж авахгүй бол (a) руу шилжинэ — `docs/ESIS_COMPLIANCE.md` §6.3.

### 1.2 Талбарын түвшний хүсэлт — багш, ажилтан (#7, #8)

Овог, нэр, албан тушаал, заах аргын нэгдэл, албан и-мэйл, ESIS `personId`.

**Хүсэхгүй:** цалин, боловсролын дэлгэрэнгүй түүх, ажлын туршлагын бүрэн бүртгэл,
гэрийн хаяг, РД. Багшийн данс үүсгэхэд эдгээр шаардлагагүй.

### 1.3 Хүсэхгүй байгаа зүйлс (зориуд)

Дүн, сурах бичиг, дүрэмт хувцас, сонгон судлах хичээл, цахим сургалтын модуль,
барилга/өрөөний бүртгэл, суралцагчийн өрхийн байдал, эрүүл мэндийн лавлагаа.

Эдгээр нь ерөнхий боловсролын хүрээний мэдээлэл бөгөөд сургуулийн өмнөх
боловсролын портфолиод хэрэглэгдэхгүй. Хэрэггүй талбарыг гэрээнд оруулах нь
хамгаалах ёстой өгөгдлийн хэмжээг шалтгаангүй нэмэгдүүлнэ.

## Хавсралт 2 — Мэдээллийн аюулгүй байдлын үүрэг

- Авсан мэдээллийг **зөвхөн гэрээнд заасан зорилгоор** ашиглана; гуравдагч
  этгээдэд дамжуулахгүй, зар сурталчилгаа, дүн шинжилгээний бүтээгдэхүүнд
  ашиглахгүй.
- Цэцэрлэгтэй байгуулсан гэрээ дуусгавар болмогц тухайн байгууллагын хүрээнд

- Өгөгдлийн алдаа, зөрүү илэрвэл журмын **§5.1.3, §5.1.4**-ийн дагуу нотлох
  баримтын хамт **ажлын 3 өдрийн дотор** мэдээлэл хариуцагчид хүргүүлж,
  залруулгыг мөн **ажлын 3 өдөрт** багтаан хийж, мэдээллийн эзэнд эргэн
  мэдээлнэ.
- Синхрончлол нь тогтмол давтамжтай, дараалалд (BullMQ) ажиллах бөгөөд
  ESIS-ийн үйлчилгээнд ачаалал үүсгэхгүй. Санал болгож буй давтамж: өдөрт нэг
  удаа, ажлын бус цагт.
