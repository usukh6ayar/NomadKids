## 0. Хамгийн эхэнд — шулуухан хариу

★★ **20,000 зэрэг хандалтыг үзүүлээгүй, өнөөдрийн бүтэц дээр үзүүлэх ч
боломжгүй.** Энэ бол сорилын үр дүн, бүтэлгүйтэл биш.

Хэмжсэн зүйл нь:

1. **Ханшийн муруй** — 4 төрлийн хандалт × 5 түвшний зэрэгцээ холболт, бодит
   хэмжээний өгөгдөл дээр;
2. **Саадыг нэрлэсэн, нотолгоотой** — API нь **ганц Node процесс**, тэр нь
   **нэг цөм**өөс хэтрэхгүй;
3. **20,000 хүртэл юу хэрэгтэйг тооцсон арифметик**, таамаглалаа ил бичсэн.

★ **Хамгийн чухал ганц олдвор:** production-д API нь
`exec node apps/api/dist/main.js` — **нэг процесс, нэг урсгал**. VPS дээр 4
vCPU байгаа ч API нь тэдгээрийн **нэгийг** л ашиглаж чадна. Өөрөөр хэлбэл
хамгийн хямд бөгөөд хамгийн том сайжруулалт нь техник хангамж худалдаж авах биш,
**процессыг олшруулах** явдал юм (§5).

### Юу харагдаж байна вэ

★ **Нэг ч алдааны хариу гараагүй — 20 сорилын бүхий л 20-д `non-2xx = 0`.**
Ачаалал ихсэхэд систем алдаа буцаадаггүй, зөвхөн **удаашардаг**. Энэ нь ялгаа
бүхий зүйл: 500-аар унасан систем өгөгдөл гэмтээж болзошгүй, удаашралтай систем
дараалалд зогсоно. (`register` дээр 400 холболттой үед 24 socket алдаа гарсан нь
**клиент талын** timeout — сервер тэднийг харах хүртэл клиент нь салсан.)

★★ **Хүчин чадал 10 холболтоос эхлээд тэгш шулуун.** `auth-me` нь 10 болон 400
холболтод адилхан ~1500 rps өгч байна; зөвхөн латенц нь шугаман өснө. Энэ бол
ханасан системийн сурах бичгийн дүр төрх — процесс аль хэдийн 100% ажиллаж
байгаа, шинэ холболт зөвхөн дараалалд нэмэгдэнэ.

★★★ **Ирцийн журнал бусад бүхнээс 10–20 дахин үнэтэй.** 200 хүүхэд × 31 хоног =
6,200 нүд угсарч, JSON болгож байна. 75 rps нь цэцэрлэгийн хувьд хангалттай
(журналыг секундэд 75 удаа нээдэг хүн байхгүй), гэвч энэ бол системийн хамгийн
үнэтэй уншилт бөгөөд ирээдүйн оптимизацийн эхний байрлал.

(Хувь нь **нэг цөмийн** харьцаагаар. 100%-иас дээш нь олон цөм ашиглаж байна.)

★ **API процесс нэг цөмөөр хязгаарлагдаж байна.** Node нь нэг урсгалтай, entry
point нь `exec node apps/api/dist/main.js` — cluster байхгүй, worker thread
байхгүй. Машинд хэдэн цөм байх нь хамаагүй.

★★ **`auth-me` дээр Postgres нь 112% болж байгаа нь санамсаргүй биш.** CLAUDE.md
**§1.3** нь эрх, цэцэрлэгийг **хүсэлт бүрт `Membership`-ээс дахин уншихыг**
шаарддаг — багшийн томилгоог цуцлахад тэр нь токен дуустал хүчинтэй хэвээр
байхгүйн тулд. Тэр дүрэм зөв, өөрчлөгдөхгүй. Гэхдээ түүний **үнэ нь хэмжигдэхүйц**
бөгөөд энд харагдаж байна: секундэд 1,500 хүсэлт гэдэг нь секундэд 1,500 session

- membership уншилт.

☆ Тиймээс хэмжээг өсгөх үед **Postgres-ийг мартаж болохгүй**. API-г 4 процесс
болгоход `auth-me`-ийн ханш ~4 дахин өснө, харин тэр нь Postgres-ээс ~4.5 цөм
шаардана.

## 4. 20,000 зэрэг хандалт гэдэг нь юу вэ — арифметик

★ **«Зэрэг хандалттай хэрэглэгч» ≠ «зэрэг хүсэлт».** 20,000 хүн дэлгэц нээж
сууж байгаа нь секундэд 20,000 хүсэлт биш. Энэ ялгааг тодорхой болгохгүйгээр
ямар ч тоо утгагүй, тиймээс таамаглалаа ил бичье.

### 4.1 Нэг хүсэлтийн CPU өртөг (ханасан үеийн rps-ээс урвуулан)

| Сценар                |  rps | Нэг цөмийн CPU / хүсэлт |
| --------------------- | ---: | ----------------------: |
| `auth-me`             | 1600 |                 0.62 мс |
| `children`            |  700 |                 1.43 мс |
| `dashboard/admin`     |  250 |                  4.0 мс |
| `attendance/register` |   75 |                 13.3 мс |

### 4.2 Холимог

Бодит хэрэглээний ойролцоо жин: **45% session шалгалт · 30% жагсаалт · 20%
самбар · 5% журнал.**

```
0.45×0.62 + 0.30×1.43 + 0.20×4.00 + 0.05×13.3 = 2.17 мс / хүсэлт
```

→ **Нэг M1 цөм ≈ 460 rps** энэ холимогоор.
→ **Нэг VPS цөм ≈ 460 × 0.45 ≈ 207 rps.**

### 4.3 20,000 хэрэглэгч хэдэн rps болох вэ

| Загвар      | Тайлбар                               |     rps |
| ----------- | ------------------------------------- | ------: |
| **Бодитой** | Хэрэглэгч 25 секунд тутамд нэг үйлдэл | **800** |
| Ачаалалтай  | 10 секунд тутамд                      |   2,000 |
| Гамшигт     | 5 секунд тутамд                       |   4,000 |

### 4.4 Хэрэгцээт хүчин чадал (60% ашиглалтаар — 100% нь дараалал үүсгэнэ)

| Загвар     |   rps | M1 цөм | **VPS цөм** |
| ---------- | ----: | -----: | ----------: |
| Бодитой    |   800 |    2.9 |   **≈ 6.5** |
| Ачаалалтай | 2,000 |    7.2 |    **≈ 16** |
| Гамшигт    | 4,000 |   14.5 |    **≈ 32** |

Дээр нь Postgres-ийн цөм (§3-ын ★★-аар API-гийн ойролцоогоор 1:1).

★★ **Дүгнэлт:** «Бодитой» загвараар 20,000 зэрэг хандалт нь ойролцоогоор
**API-д 7, өгөгдлийн санд 7 VPS цөм** шаардана — өнөөгийн нэг 4 vCPU машины
оронд 3–4 ийм машин, эсвэл нэг том машин + горизонталь тэлэлт. Энэ нь **биелэх
боломжтой тоо**, харин өнөөдрийн бүтэц дээр биш.

## 5. Дараагийн алхмууд, үр өгөөжийн дарааллаар

| №   | Ажил                                                                                                          | Тооцоолсон нөлөө                                       | Өртөг                           |
| --- | ------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------ | ------------------------------- |
| 1   | **API-г олон процесс болгох** (Node `cluster`, эсвэл compose дээр `replicas` + Caddy-ийн ачаалал хуваарилалт) | **×3–4** одоогийн VPS дээр, шинэ техник хангамжгүйгээр | Бага                            |
| 2   | Ирцийн журналын хариултыг хөнгөлөх (нүд бүрийг объект биш, эгнээгээр нягтруулах)                              | Хамгийн үнэтэй уншилтад **×2–3**                       | Дунд                            |
| 3   | Session + membership уншилтыг Redis-д богино хугацаагаар кэшлэх                                               | Postgres-ийн ачааллыг бууруулна                        | **Дунд — §1.3-той болгоомжтой** |
| 4   | Техник хангамж нэмэх                                                                                          | Шугаман                                                | Өндөр                           |

★ **№1 нь эргэлзээгүй эхний алхам.** Нэмэлт зардалгүйгээр одоогийн машины
ашиглагдаагүй 3 цөмийг ажиллуулна. Анхаарах зүйл: тайлангийн worker нь
API-ийн процесс дотор ажилладаг (`REPORTS_WORKER_ENABLED`), тиймээс процессыг
олшруулахдаа **зөвхөн нэгд нь** worker-ыг асаах ёстой, эс бөгөөс нэг PDF
даалгавар N удаа зэрэг гүйцэтгэгдэнэ.

★★ **№3 нь дүрэмтэй мөргөлдөж болзошгүй тул анхааралтай.** §1.3 нь эрхийг
хүсэлт бүрт дахин уншихыг шаарддаг; кэш нь тэр баталгааг сулруулна. Хэрэв
хийвэл маш богино TTL (5–10 сек) байх ба эрх цуцлах үйлдэл нь кэшийг шууд
хүчингүй болгох ёстой. Энэ бол гүйцэтгэлийн шийдвэр биш, **аюулгүй байдлын**
шийдвэр — тусад нь хэлэлцэнэ.

## 6. Яаманд юу гэж хэлэх вэ

`ESIS_COMPLIANCE.md` §6.2-ын асуулт хэвээр нээлттэй:

> #6-ийн 20,000 зэрэг хандалтын шалгуур сургуулийн өмнөх боловсролын
> байгууллагын системд хэрхэн хэрэглэгдэх вэ?

★ Шалгуурын бичвэр өөрөө «**ялангуяа нэгдсэн сорил, шалгалтын үед**» гэсэн
нөхцөл тавьсан. Энэ нь ерөнхий боловсролын улсын шалгалтын нөхцөл. Цэцэрлэгт
шалгалтын өдөр гэж байхгүй — 200 хүүхэдтэй цэцэрлэгийн хамгийн ачаалалтай мөч нь
өглөөний ирц бүртгэл бөгөөд тэр нь 8 багш зэрэг ажиллана.

Тиймээс яаманд танилцуулах зүйл нь **«20,000 ✅»** гэсэн мөр биш — тийм мөр нэг
асуултад тэсэхгүй — харин:

1. энэ баримт бичиг: арга зүй, хэмжсэн муруй, нэрлэсэн саад;
2. §4-ийн арифметик: 20,000-д хүрэхийн тулд яг юу хэрэгтэйг;
3. §5-ын төлөвлөгөө: №1-ийг хийснээр өнөөгийн техник хангамж дээр 3–4 дахин
   өснө;
4. §6-ийн асуулт: СӨБ-ын системд энэ шалгуурыг ямар тоогоор хэрэглэх вэ.

Хэмжсэн муруй, шударга экстраполяци хоёр нь шалгагчийн өмнө зогсоно. Зохиосон
тоо зогсохгүй.

## 7. Дахин ажиллуулах

```bash
# 1. Тусдаа өгөгдлийн сан
docker exec <db> psql -U kinder -d postgres -c "CREATE DATABASE kinder_load"
DATABASE_URL=postgresql://kinder:kinder@localhost:5434/kinder_load \
  pnpm --filter @kinder/api exec prisma migrate deploy

# 2. Бодит хэмжээний өгөгдөл
DATABASE_URL=postgresql://kinder:kinder@localhost:5434/kinder_load \
LOAD_TEST_CONFIRM=yes CHILDREN=200 DAYS=60 \
  pnpm --filter @kinder/api exec tsx prisma/seed-load.ts

# 3. Production API
pnpm --filter contracts build && pnpm --filter api build
DATABASE_URL=postgresql://kinder:kinder@localhost:5434/kinder_load \
NODE_ENV=production PORT=3777 REPORTS_WORKER_ENABLED=false \
CORS_ORIGINS=https://loadtest.local WEB_ORIGIN=https://loadtest.local \
  node apps/api/dist/main.js

# 4. Нэг удаа нэвтэрч cookie авах, дараа нь autocannon-оор дахин ашиглах
```

⚠ `NODE_ENV=production` нь `CORS_ORIGINS`/`WEB_ORIGIN` дээр `localhost` болон
`http://`-ыг **татгалзана** — production тохиргооны хамгаалалт зөв ажиллаж байгаа
хэрэг. Тиймээс дээрх жишээнд https утга өгсөн; autocannon `Origin` толгой
илгээхгүй тул CORS саад болохгүй.
